Problem
// problem

Schedule a tensor compute graph under a tight memory budget.

Given a graph of tensor ops and a small fast-memory capacity, decide: which ops run together, at what tile size, and in what order — all at once. Minimize total runtime. Every step must fit in fast memory.
hard constraint

Memory fits every step

inputs + outputs + resident
   ≤ fast memory capacity

Tiling below native granularity pads compute. A smaller tile is not cheaper, because each tile pays the full base cost.

objective

Minimize tile runtime

tile cost = max(compute, memory transfer)
total = Σ (tile cost × num tiles) over groups

Fusing ops into one group eliminates slow-memory round trips between them. That is where the speedup comes from.

Learnings
// what changed · what broke · what worked

What I built first was not what shipped.

vertical · role split

Single agent to orchestrated pipeline

Started with one LLM call doing everything. Quality collapsed on complex graphs. Splitting into specialized phases — Analyzer, Planner, Optimizer, Refiner — each with a focused prompt, recovered it.

horizontal · diversity

Three strategies beat one

A single planner gets stuck on its prior. Three parallel planners with distinct strategies cover the search space — aggressive fusion for compute-bound, conservative for memory-tight. Same wall-clock cost, broader coverage.

bugs found late · validator

Three silent bugs, caught by harder graphs

Dependency ordering was never validated. MatMul op-type lookup used the wrong subgraph op. Output tile count came from the first op only. All three passed shallow tests; only denser DAGs exposed them.

time-aware · budget cascade

Every phase reads the clock first

9.5-min hard cap. Each phase grabs only a fraction of remaining time, skips itself if budget too tight. Greedy fallback runs in milliseconds. Pipeline cannot exceed budget or return nothing.
