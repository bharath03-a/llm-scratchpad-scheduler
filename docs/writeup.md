# Gemini-Powered Multi-Agent DAG Scheduler

**MLSys 2026 — Track B: Agent Reasoning**

---

## Overview

We present a five-phase multi-agent pipeline that schedules memory-constrained DAG workloads using Gemini 2.5 Flash. The central design principle separates concerns cleanly: the LLM is responsible solely for *which* operations to group into subgraphs, while all constraint-sensitive decisions (granularity selection, memory validation, latency calculation) are handled by deterministic Python. This architecture prevents the model from generating memory-invalid schedules and eliminates the need for the LLM to guess numeric thresholds.

---

## Agent Architecture

The pipeline executes five phases within the 10-minute time budget.

**Phase 1 — Problem Analysis (1 LLM call).** A dedicated `AnalyzerAgent` receives the raw problem JSON enriched with pre-computed graph metrics from NetworkX: critical-path length, per-node fan-in/fan-out, identified MatMul chains, and topological levels. The model outputs a free-text structural analysis that is forwarded verbatim as context to all downstream planners, ensuring they reason from a shared understanding of the graph.

**Phase 2 — Parallel Strategy Planning (3 concurrent LLM calls).** Three instances of `PlannerAgent` run concurrently via `asyncio.gather`, each receiving the same analysis but a different *strategy persona* injected into the prompt:

- **Aggressive**: maximise operation fusion; accept sub-native granularity and recomputation to minimise subgraph count.
- **Balanced**: follow the critical path at native granularity; use Split-K for MatMul chains.
- **Conservative**: prefer native granularity and spilling; group only when operations trivially co-fit.

Each planner outputs a candidate schedule as a JSON object using Gemini's `response_mime_type: "application/json"` mode with `thinking_budget=0`. Disabling extended thinking is critical: on large problems (32 ops), the model's internal reasoning would consume most of the `max_output_tokens` budget, leaving insufficient tokens to complete the JSON output and causing truncation. Output token budgets are scaled with problem size as `min(65536, max(8192, num_ops × 1000))`.

**Phase 3 — Deterministic Validation and Granularity Optimisation (no LLM).** Every candidate subgraph partition is passed through `optimize_granularities`, which algorithmically finds the *largest* valid `[w, h, k]` triplet for each subgraph via a structured search over power-of-two candidates. A pruning step (`_feasible_retentions`) discards any `tensors_to_retain` entry whose full tensor size exceeds the scratchpad capacity, preventing working-set overflows on problems with large tensors. The valid candidate with the lowest total latency is selected as the best solution.

**Phase 4 — Optimisation (1 LLM call).** If a valid candidate exists and time remains, `OptimizerAgent` is invoked to propose improved traversal orders (e.g., snake patterns for MatMul to exploit data reuse) and refined retention decisions. The result passes through deterministic validation before replacing the current best only if it achieves a lower latency.

**Phase 5 — Iterative Refinement (up to 3 LLM calls).** If no valid candidate was produced, `RefinerAgent` receives the invalid candidate alongside a list of specific validation errors (e.g., *"Step 2: working set 1,065,088 bytes exceeds capacity 250,000 bytes"*) and attempts targeted corrections. Up to three iterations are attempted; if all fail, a deterministic fallback (one operation per subgraph, largest valid granularity) is returned, guaranteeing a valid submission within the time limit.

## Prompting Strategy

**Constraint-first framing.** All system prompts state memory limits numerically upfront and include a step-by-step reasoning framework that instructs the model to (1) analyse dependencies, (2) compute the working set for each proposed grouping, (3) select granularity, and (4) decide on retention. This chain-of-thought structure reduces the rate at which the model produces constraint-violating schedules.

**Strategy personas.** Rather than prompting for a single "best" schedule, we issue three concurrent prompts with explicit strategy labels and trade-off priorities. This increases the probability that at least one candidate is valid and near-optimal, particularly on diverse graph topologies.

**Error-as-context refinement.** During Phase 5, the refiner receives the prior invalid schedule alongside a structured error list generated by our deterministic validator. Providing specific, machine-generated diagnostics (exact step index, actual vs. allowed working set, dependency violation) produces more targeted corrections than generic instructions.

**JSON-only output discipline.** All planning and optimisation calls use `response_mime_type: "application/json"` with `thinking_budget=0`. This ensures the full output token budget is available for JSON generation, preventing truncation on large problems.

The baseline is a deterministic one-op-per-subgraph schedule with algorithmically optimal granularity per step. The agent's largest gains come from fusing chains of operations into fewer subgraphs, reducing the number of slow-memory round trips. On `mlsys-2026-9` (32 MatMul-heavy ops with 1024×1024 tensors), the aggressive planner collapsed 32 individual subgraphs into 8, yielding a 7.3× latency reduction.

## Implementation

**Language / runtime.** Python 3.12 with `asyncio` for concurrent LLM calls; `google-genai` SDK for Gemini access; `networkx` for DAG analysis; `rich` for structured terminal output.

**Dependencies.** `google-genai`, `networkx`, `python-dotenv`, `rich` (all in `requirements.txt`).

**Entry point.** `python3 agent.py <input.json> <output.json>` — reads the problem, runs the pipeline, writes the solution. All phases are guarded by time checks; the deterministic fallback ensures a valid output is always written before the 10-minute timeout.
